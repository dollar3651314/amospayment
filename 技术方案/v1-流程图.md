## 1. 总体架构
谁和谁打交道：两套系统通过服务接口互通；Payment 通过钱包服务接口使用托管服务商，通过渠道适配器使用 off-ramp 渠道。

```mermaid
flowchart TB
    subgraph USERS["使用者"]
        MU["商户用户<br/>管理员 / 提交人 / 审批人 / 查看"]
        OPS["Payment 运营团队<br/>客服 / 合规 / 交易员 / 出款审批 / 财务 / 管理员"]
    end
    subgraph PAY["Payment 系统"]
        MC["商户后台和开放 API"]
        ADM["运营后台"]
        CORE["业务核心<br/>开户、收款方、付款单、报价、审批"]
        LED[("复式账本<br/>商户 × 资产 × 链")]
        RISK["合规<br/>制裁、地址筛查、Travel Rule"]
        WAL["钱包服务接口"]
        CHA["渠道适配器"]
        INT["互通接口<br/>授权开户、登录跳转、余额互转"]
    end
    GW["Gateway 系统（amos111）"]
    CUS["托管服务商<br/>Fireblocks / Cobo"]

    MU --> MC --> CORE
    OPS --> ADM --> CORE
    CORE --> LED
    CORE --> RISK
    CORE --> WAL --> CUS
    CORE --> CHA --> CH
    CORE --> OTC
    INT <--> GW
    CORE --- INT
    CUS -->|"USDT / USDC"| CH
    CUS -->|"直接付 USDT / USDC"| BEN
    CH -->|"法币"| BEN
```

## 2. 付款主流程
从商户充值到收款方收到钱。虚线是失败和退回的路径。

```mermaid
flowchart TD
    A([商户充值 USDT / USDC<br/>到自己的充值地址]) --> B{地址风险筛查}
    B -->|通过| C[入账：商户余额<br/>按资产＋链]
    B -->|不通过| B2[冻结，进异常队列<br/>合规处理]
    C --> D[商户新建付款单<br/>收款方、金额、目标币种、用途、附件]
    D --> E[实时报价<br/>成本 ＋ 汇率加点 ＋ 手续费]
    E --> F{企业商户内部审批<br/>见第 6 节}
    F -->|批准| G[提交给平台<br/>冻结商户余额]
    F -->|驳回| D
    G --> H{合规审核<br/>收款方、用途、附件、筛查}
    H -->|需补资料| H2[通知商户补资料] --> H
    H -->|拒绝| X[解冻退回商户]
    H -->|通过| H3{付什么？}
    H3 -->|法币| I[交易员：选渠道<br/>系统推荐排序，人工确认]
    H3 -->|USDT / USDC 直付| J2[按后台配置的出款路线] --> K
    I --> J[锁定报价 15～30 分钟]
    J --> K{出款审批<br/>提交人 ≠ 审批人}
    K -->|驳回| I
    K -->|批准| L[钱包服务接口发起转账<br/>只能转白名单地址]
    L --> M{托管服务商规则}
    M -->|通过并签名| N[USDT / USDC 上链<br/>转给渠道或收款方]
    M -->|拒绝| K
    N --> O{目标是法币？}
    O -->|否：直接付 USDT / USDC| P[链上确认 → 完成]
    O -->|是| Q[渠道 API 下单<br/>渠道处理中]
    Q --> R{渠道回调 / 查询}
    R -->|成功，附凭证| P
    R -->|失败| S[渠道把钱退回平台]
    S --> S2{还有可用渠道？}
    S2 -->|有| I
    S2 -->|没有| X2[付款单改为失败<br/>恢复商户余额，通知商户]
    J -.->|超时未审批| E
    P --> T[正式扣款<br/>记手续费和汇率收入<br/>通知商户、回调]
```

## 3. 一键授权开户
A 是推荐方，B 是被推荐的系统；Gateway → Payment、Payment → Gateway 都按这张图。

```mermaid
sequenceDiagram
    autonumber
    actor U as 商户（授权联系人或管理员）
    participant A as A 系统（推荐方）
    participant B as B 系统（被推荐方）
    participant BC as B 的合规团队

    A->>U: 后台显示 B 的推荐卡片
    U->>A: 点"一键开通"
    A->>U: 授权页：共享哪些资料、用途、B 的条款
    U->>A: 勾选同意 ＋ 输入动态码
    A->>A: 记录授权（谁、何时、哪些资料、条款版本）
    A->>B: 开户申请（商户编号、授权编号、资料包、文件短时链接、A 已通过的时间）
    B->>A: 拉取文件（短时链接）
    B->>B: 创建预填申请，保存授权记录
    B-->>A: 状态回调：待补资料
    B->>U: 发送补充资料链接（只填 B 特有的项目）
    U->>B: 提交补充资料
    B->>BC: 进入审核队列（标注"由 A 推荐"）
    alt 通过
        BC->>B: 通过
        B-->>A: 状态回调：已开通
        A->>U: 后台显示"已开通 B"，按钮变为"进入 B"
    else 需补件
        BC->>B: 要求补件
        B->>U: 补件通知
    else 不通过
        BC->>B: 不通过
        B-->>A: 状态回调：未通过（只给类别）
    end
    U->>A: 点"进入 B"
    A->>B: 一次性登录凭证（短时、只能用一次、绑定商户和用户）
    B->>B: 校验凭证；第一次进入时为该用户建账号（默认只能查看）
    B->>U: 进入 B 的商户后台；付款、审批等敏感操作仍要 B 的动态码
```

## 4. 余额互转和清算
商户在 Gateway 收到的钱转到 Payment 付款（反方向同理）。两边各自记账、各自对平；链上结算由财务在后台主动发起，不设固定时间和起付金额。

```mermaid
sequenceDiagram
    autonumber
    actor U as 商户
    participant G as Gateway
    participant P as Payment
    participant CH as 链上
    actor F as Payment 财务

    U->>G: 把 X USDT（TRON）转到 Payment（需动态码）
    G->>P: 余额互转请求（唯一编号、商户编号、资产＋链、金额）
    P->>P: 记账：Gateway 清算账户 −X，商户余额 ＋X
    P-->>G: 成功（Payment 记账编号）
    G->>G: 记账：商户余额 −X，Payment 清算账户 ＋X
    G->>U: 实时到账（两边余额都更新）
    Note over G,P: 任何一步失败：按唯一编号重试；超时未确认的进异常队列，人工核对后冲正
    Note over G,P: 每天程序自动核对两边清算账户，不相等报警、进财务异常队列
    P->>F: 后台显示待结算净额和方向（按资产＋链）
    F->>P: 选择资产＋链，发起结算（需动态码）
    P->>G: 核对两边清算账户
    alt 相等
        P->>CH: 转账净额（按资产＋链；Gateway 欠款时由 Gateway 转出）
        CH-->>G: 到账
        P->>P: 两边清算账户扣减已结金额，生成结算单
    else 不相等
        P->>F: 不能发起，进异常队列人工核对
    end
```

## 5. 平台审批流和异常队列
平台各角色怎么接力处理一笔付款单；异常统一进一个队列。

```mermaid
flowchart LR
    subgraph IN["进入平台"]
        S1[商户提交的付款单]
    end
    subgraph COMP["合规审核"]
        C1{收款方第一次使用？}
        C2[收款方尽调<br/>企业：资料；个人：户名＝KYC 姓名]
        C3[付款单审核<br/>用途、附件、制裁和地址筛查]
    end
    subgraph TRADE["交易员"]
        T1[法币付款单：询价、选渠道<br/>系统推荐排序]
        T2[锁定报价<br/>需要时 USDT ↔ USDC 兑换]
    end
    subgraph APPR["出款审批"]
        A1{审批人 ≠ 提交人}
        A2[批准 → 钱包服务接口出款]
    end
    subgraph FIN["财务"]
        F1[渠道预存款调拨]
        F2[对账]
        F3[发起 Gateway 清算]
    end
    EQ[["异常队列<br/>渠道退回、超时、筛查报警、对账差异<br/>每项有处理时限，超时提醒"]]

    S1 --> C1
    C1 -->|是| C2 --> C3
    C1 -->|否| C3
    C3 -->|通过，法币| T1 --> T2 --> A1
    C3 -->|通过，USDT / USDC 直付| A1
    A1 -->|批准| A2
    A1 -->|驳回| T1
    A2 --> F2
    A2 -.->|渠道失败，退回平台| T1
    T1 -.->|渠道预存款不足| F1 -.-> T1
    C3 -.->|报警| EQ
    A2 -.->|托管服务商拒绝 / 全部渠道失败| EQ
    F2 -.->|差异| EQ
    EQ -.->|处理后回到对应环节| C3
```

## 6. 企业商户内部审批
企业商户的财务提交、负责人审批；超过商户管理员自己设定的金额才需要审批；平台不设下限，设为 0 就是每笔都审批。

```mermaid
flowchart TD
    A[提交人新建付款单<br/>或批量导入] --> B{金额超过商户设定的阈值？}
    B -->|否| E[直接提交给平台]
    B -->|是| C[通知审批人<br/>站内、邮件]
    C --> D{审批人审批<br/>需要动态码}
    D -->|批准| E
    D -->|驳回，附原因| F[退回提交人修改或作废]
    D -->|超过报价有效期| G[报价失效，重新报价后再审批]
    G --> C
    E --> H[平台流程<br/>见第 2、5 节]
```

## 7. 对账
每天和三类对象对账：渠道、托管服务商、Gateway。任何一项不平都进异常队列。

```mermaid
flowchart TB
    L[("Payment 账本<br/>商户 × 资产 × 链")]
    subgraph R1["① 托管服务商"]
        W1["各钱包、各链的实际余额"]
        W2["账本：平台资产账户"]
        W1 <-->|"相等？"| W2
    end
    subgraph R2["② 每个渠道"]
        H1["渠道对账文件 / API：<br/>收到的 USDT、付出的法币、预存款余额"]
        H2["账本：渠道预存款、在途付款单"]
        H1 <-->|"逐笔、按余额"| H2
    end
    subgraph R3["③ Gateway"]
        G1["Gateway 的 Payment 清算账户"]
        G2["Payment 的 Gateway 清算账户"]
        G1 <-->|"相等？按资产＋链"| G2
    end
    subgraph R4["④ 总账平衡"]
        T1["平台实际持有（各钱包 ＋ 渠道预存款 ＋ 在途）"]

    end
    L --> R1 & R2 & R3 & R4
    R1 & R2 & R3 & R4 -.->|"不平"| EQ[["异常队列（财务）"]]
```

## 8. 提币
商户把多余的钱提到自己的钱包。同时开通 Gateway 的商户还可以选择"和 Gateway 互转"（第 4 节）。

```mermaid
flowchart TD
    A[商户添加提币地址<br/>需要动态码] --> B[24 小时冷静期<br/>平台做地址风险筛查]
    B -->|通过| C[地址可用]
    B -->|高风险| B2[拒绝，通知商户]
    C --> D[提交人提交提币<br/>冻结 金额＋网络费]
    D --> E{超过商户设的审批金额？}
    E -->|是| F{商户审批人批准}
    E -->|否| G
    F -->|批准| G[平台审核：地址筛查]
    F -->|驳回| X[解冻退回]
    G -->|通过| H{平台出款审批<br/>审批人 ≠ 提交人}
    G -->|拒绝| X
    H -->|批准| I[托管服务商签名上链]
    I --> J[链上确认 → 完成，正式扣款]
    I -.->|托管服务商拒绝| H
```

## Amos 的答复（2026-10-23）
1. 直接付 USDT、USDC 不需要交易员选渠道，出款路线在平台后台设置（第 2、5 节）。
2. 渠道付款失败：渠道把钱退回平台，平台换渠道再试；所有渠道都失败时，付款单改为失败，恢复商户余额（第 2 节）。
3. 和 Gateway 的链上结算由财务在后台主动发起和操作，后台显示待结算金额即可；不设固定时间和起付金额（第 4 节）。
4. 商户内部审批的金额由商户自己设，平台不设下限（第 6 节）。
